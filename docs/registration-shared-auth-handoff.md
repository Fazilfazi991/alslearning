# Shared Auth handoff: registration setup and deactivation

## Boundary and ownership

Registration owns `src/app/api/auth/setup/route.ts` and registration tests. The security workstream owns deactivation, session guards and Auth hook migrations. The registration route uses existing authenticated profile RLS for a second, fresh authorization read after the external password update. A denied or uncertain read produces no success, clears the setup grant, attempts local sign-out and tells the student the password may have changed. A later deactivation must still deny access through the shared database guards. The registration invitation/setup hard guard remains false.

The later durable setup-operation changes supersede the earlier grant limitation: setup grants are consumed through database-backed operations, and uncertain outcomes require reconciliation. Copied-grant replay was exercised in local route/database tests; a clean-browser consumed-invitation check is a different case and must not be reported as browser proof of copied-grant replay.

### Local recovery failure follow-up

The preserved local recovery operation is `unknown / unknown / not_checked`; its Auth session no longer exists. Local GoTrue logs include a completed password-update rejection with `same_password`, and the pinned provider source rejects that case before the password transaction. The existing operation journal does not bind a provider request identifier to this operation, so aggregate logs, absent sessions and an absent later audit event do not establish an exhaustive, terminal outcome for this particular dispatch. Do not relabel it or issue a replacement. Obtain provider evidence bound to the exact request and identity, establish that old dispatchers cannot still write, then independently review an audited conditional reconciliation interface. The current audited replacement function deliberately rejects unknown operations and offers no transition for resolving them.

**Unknown-operation recovery: BLOCKED BY PROVIDER EVIDENCE.** Admissions should escalate through the organization's authorized technical support and Supabase support channel, supplying only the internal operation reference and any provider request correlation available through the secure support workflow. Support must establish the terminal result for the exact identity and request and that no earlier dispatch can still execute; elapsed time, a revoked session, cleared browser state, or a rejection belonging to another request are not proof. If the provider cannot establish those facts, retain the original operation and keep replacement blocked. A future resolution requires a reviewed audited conditional mechanism and fresh identity proof; there is no supported unknown-state reset in this checkpoint.

After an uncertain response, the route clears the grant and signs out. A later request without a verified session or capability previously mislabeled that condition as expiry. The setup route now reports an unavailable or used link and warns that an earlier submission may have changed the password. The form stops same-link retries after non-validation errors or a lost response. The original claim primitive returned the same denial for expiry, invalidity, replay and authorization failure. An independent local route/PostgREST regression verifies that an unknown write followed by a missing grant produces the warning and no second provider dispatch; provider faults in that lab are simulated. The browser recovery/login and copied-capability replay remain uncompleted.

The subsequent shared migration `20261113062257_registration_setup_atomic_claim_status.sql` adds identity-bound internal invalid, unavailable, unresolved, used and expired classifications to the same locked claim transaction. It preserves the older UUID-or-null interface and does not change the public generic denial. The registration route now calls that single atomic interface and logs only its bounded denial category.
