# Interrupted registration setup: decision boundary

This describes a local candidate, not a hosted or release-approved procedure. Password setup, invitation delivery and the HTTP recovery action remain disabled in release builds. The local acceptance switch is only for a disposable stack: bind the actual Next listener and all fixture ports to `127.0.0.1`, use synthetic identities and secrets, and never use it on a hosted development server. Configuration values alone do not prove listener binding or provider provenance. The authenticated database recovery RPC is separately callable by an authorized Admin if the migration is installed; the HTTP feature gate does not disable that database primitive.

| Observation | Provider outcome | Application authorization | Current action |
| --- | --- | --- | --- |
| Shape or authorization rejected before claim | No dispatch by this route | Denied or not evaluated | No operation is consumed; no password update is dispatched. |
| Grant claimed, process interrupted or response lost | Unknown; a write may still finish | Unknown | Original grant remains spent. Block replacements and escalate. Neither timeout nor a later successful login proves the first write cannot still finish. |
| Provider returns success and final check permits access | Confirmed success | Allowed at the database finalization check | Original grant remains spent; sign out and use normal login. A later fresh RLS read can still deny access. |
| Provider returns success, then deactivation or revocation wins | Confirmed success | Denied | The credential write can have completed. Do not report it as a provider rejection or restore access. |
| Pinned local provider returns a verified weak-password rejection | Confirmed rejection, only under the explicit local probe | Not checked | The consumed operation remains spent; an Admin can authorize one linked fresh proof. |
| Other provider error, exception or unverified provenance | Unknown | Not established | Record unknown, or leave claimed if recording fails. Block replacement. |

The forward migrations record provider outcome and application decision separately. `denied_or_unavailable` preserves the fact that the existing authorization helper folds errors into false. `allowed` describes only the database decision at finalization; it does not establish current access, completion of the later RLS check, or successful sign-out. An operator must not release an unknown operation unless credible provider-side evidence establishes that the earlier request can no longer complete; no provider cancellation or operation-status API has been established here. Revoking the app grant or expiring a lease does not establish that fact. Unknown and claimed records remain blocked; there is no implemented reconciliation that releases them.

For a confirmed terminal result, the draft Admin status and authorization action uses existing Admin/session checks, locks the accounts and setup record, validates identity and current student state, and atomically records a bounded reason and audit event. It authorizes at most one replacement. The invitation carries a signed authorization bound to the application and student; after a fresh provider proof, a service-only function rechecks the new session and consumes the authorization while creating a distinct linked operation. The original grant stays spent. Confirmation of success depends on transport provenance; the hosted provider and proxy have not been verified for this behavior.

In the local fixture's pinned GoTrue v2.197.0 source (tag commit `4eee58f296d9698a1c2c0ae14d7a0b379c7622d3`), `UserUpdate` validates password strength before the password-update transaction. An actual local Next-route test with API version `2024-01-01`, a stricter synthetic minimum length, a one-forward proxy and a pinned Auth image observed exactly one matching HTTP 422 `weak_password` response and the corresponding SDK error. The previous synthetic credential still authenticated and the rejected credential did not; password hashes were not inspected. An Admin then authorized one fresh proof, which led to a working replacement login and student-scoped content API checks. The route classifies this error only under the explicit local probe; all other errors remain unknown. The service-role database function trusts the caller's outcome assertion and cannot itself verify provider provenance. Hosted transport, provider version and settings remain unverified.

The combined local fixture configured `pg-functions://postgres/public/als_active_account_auth_hook`. While a separate session held the student's account advisory lock, an actual GoTrue password login returned the hook's distinctive account-transition error; a second connection confirmed the lock remained held through the response. After release, login succeeded and the issued claims had the expected subject, authenticated role, student application role and session identifier. This proves invocation for that local login path, not every Auth flow or hosted configuration. The recovery integration uses programmatic HTTP cookies, not a fresh browser. A synthetic application was submitted and approved in a real browser, but the separately isolated Student context and course-page journey remain unverified.

The original digest, session binding and claim remain authoritative. A replacement must be a distinct linked operation and must not change profile status, bans, role, student identity, student code, enrollment or revocation generation. Two concurrent operator decisions must not yield two replacements. Admin authorization, reason and audit must be checked atomically, using existing shared authorization primitives owned by the security workstream.
